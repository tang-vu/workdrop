# Solami integration research

Checked 2026-09-23. This is interface research, **not evidence of an authenticated connection**. No Solami key, paid plan, event delivery, or transaction was verified in this check.

Implementation review 2026-09-24: `app/solami.py` implements the RPC polling portion only. It records finalized transaction references and raw public transaction JSON for configured addresses. It does **not** decode buy/sell directions, balances, redemption transitions, or migration from those transactions; it does not use Blur, Mirage, gRPC, or webhooks. Its status may be `connecting`, `catching up`, `reconnecting`, `stale`, or `live`. Here `live` means that a complete finalized-history poll succeeded recently, not a push stream or proof of end-to-end integration. No credentialed Solami call was made in this review.

## Recommended WORKDROP path

Use a server-side Solami Solana RPC endpoint as the authoritative read/reconciliation transport, with `getSignaturesForAddress` / `getTransaction` for the batch mint, Meteora pool, and redemption program, plus token-account and request-account reads for final balances and states. These are standard Solana JSON-RPC methods; Solami publishes an endpoint template of `https://rpc.solami.dev/sol?api_key=KEY` in its current site application. Poll with a durable `(slot, signature)` cursor and overlap windows, deduplicate by signature plus instruction/event index, and verify `finalized` account state before recording settled outcomes. A polling interval and last successful update can power honest live trade and job status in the UI, without asserting that a notification itself is final.

Current adapter detail: it stores a per-address high-water signature and a resumable page cursor. It scans at most four 100-signature pages per 15-second pass and resumes until reaching its prior high-water signature; it does not skip a signature when `getTransaction` temporarily returns null. Signature rows are deduplicated globally, with a separate address association. This is still a transaction reference observer, not the full account-state reconciliation described above. It initially backfills all visible history for each configured address, which may be expensive for a very active program address; choose narrow accounts and verify quota before enabling it.

If the account is entitled to a live stream, add a **server-side** Blur swap subscription filtered by the batch mint and Meteora DEX/pool, then reconcile it against RPC. The official home page demonstrates `wss://ws.solami.dev/data/subscribe?chain=solana&api_key=YOUR_KEY` and a swap filter, and advertises decoded `swap`, `liquidity`, `token_create`, and `pool_create` events. It also describes Mirage (Yellowstone frames over WebSocket), Yellowstone gRPC, and filtered webhooks. A stream should accelerate the UI; it should not decide settlement or replace backfill. Keep the API key on the server. Do not put the sample query-string key in a browser bundle.

The site application's API reference lists `WS /data/subscribe` with a `DataApi` key permission, and REST `GET /data/token/trades` and `/data/wallet/balance` with the same permission. The full request/response schema, Meteora-specific DEX identifiers, filter fields, replay cursor behavior, and exact event identifiers still need an authenticated documentation/connection test. Do not hard-code an unverified decoded shape. In particular, the home-page `pumpswap` example is **not** proof that a Meteora filter name or redemption event decoder exists. Redemption program events should be decoded from confirmed Solana transactions or account changes by WORKDROP, then reconciled at finality.

## Access and pricing facts

* Solami's [machine readable pricing API](https://api.solami.dev/pricing), fetched 2026-09-23, reports scale 8 fixed-point USD units. It reports Free `$0`, 5 RPC RPS, **0 WebSocket connections**, **0 gRPC streams**, and one webhook. Dev is `$49/month` with 50 RPC RPS and two WebSocket connections; Pro is `$99/month` with 200 RPC RPS, five WebSocket connections, and two gRPC streams. The same response reports PAYG RPC `$8/1M calls` plus `$0.08/GB`, gRPC `$0.08/GB`, Blur `$0.20/GB`, and a `$0.06` minimum balance (`min_balance_units=6000000`). These are point-in-time values; query the API again before budgeting.
* The [Solami home page](https://solami.dev/) says WebSockets are on every plan including Free, while the live pricing API says Free has `ws_connections: 0` and `ws_access: false`. The [llms.txt](https://solami.dev/llms.txt) snapshot additionally says Free has 10 RPC RPS and cites different PAYG numbers. Treat the live pricing API as the current plan data, and verify actual account entitlement before claiming free stream access.
* The home page says account creation and a key require no card. The [llms.txt](https://solami.dev/llms.txt) identifies `api.solami.dev`, `rpc.solami.dev`, and `grpc.solami.dev`. The browser app's endpoint generator shows the RPC key in the endpoint query string. The live data API reference in that app lists `x-api-key` or `Authorization: Bearer` for REST `DataApi` calls. Exact key scope and quota for this project remain unverified.
* Solami's [Rust SDK crate](https://docs.rs/crate/solami/latest) currently shows 0.1.58 (published 2026-09-05), including `subscribe_blur` and a mint filter. WORKDROP is TypeScript, so direct JSON-RPC and a validated WebSocket client may be simpler than adding a Rust service. No SDK dependency has been chosen here.

## Integration acceptance checks

1. Obtain a project-scoped Solami key and inspect its permitted products and plan. Never commit or show the key in screenshots or logs.
2. Call `getHealth`/`getSlot` and `getAccountInfo` through the Solami RPC endpoint. Record response, cluster/genesis hash, latency, and a redacted endpoint. Verify historical `getSignaturesForAddress` and `getTransaction` behavior for a known WORKDROP transaction.
3. If stream access is available, connect to `/data/subscribe` from the backend, record the accepted filter and one real Meteora swap payload, and verify signature/slot/mint/pool fields and reconnect behavior. Determine whether replay from a slot is supported; otherwise fill gaps through RPC overlap scans.
4. Record `observed`, `confirmed`, and `finalized` separately. On reconnect or out-of-order delivery, reconcile request PDA, token accounts, and DBC/DAMM pool state against finalized RPC reads. Show `reconnecting` and last successful update in the UI.
5. Test duplicate delivery, missing stream events, and reorganization/failed transaction cases. No sponsor-track readiness claim until real Solami responses appear in the app and evidence.
